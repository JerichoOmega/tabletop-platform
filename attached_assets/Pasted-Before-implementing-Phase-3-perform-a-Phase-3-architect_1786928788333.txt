Before implementing Phase 3, perform a Phase 3 architecture preflight.

The repository has completed the Phase 2 hardening pass. Do not modify code yet.

Read the current WORLD_SCALE_VIEWPORT.md specification and compare every architectural assumption in it against the actual current implementation.

I want you to determine whether the specification is sufficiently precise to begin implementation.

Pay particular attention to:

1. WorldState vs GameState
    * Precisely define what belongs to persistent WorldState.
    * Precisely define what belongs to an active tactical GameState.
    * Determine how a persistent WorldEntity becomes a combatant in an encounter.
    * Determine how combat results are committed back to WorldState.
    * Identify any duplication/synchronization hazards.
2. Entity identity
    * Determine how worldId, defId, encounter IDs, and combatant instance IDs should relate.
    * Ensure an entity leaving/re-entering the viewport or being unloaded/reloaded never becomes a new entity.
3. Coordinate ownership
    * Confirm that world coordinates are authoritative.
    * Confirm that viewport coordinates are presentation-only.
    * Confirm that screen pixels never enter the rules engine.
    * Identify every current location where x/y must eventually transition to world coordinates.
4. TileQueryFn
    * Determine the minimal interface the rules engine actually needs.
    * Make sure the rules engine does not become coupled to WorldState, ChunkStore, React, or rendering.
    * Determine whether a TileQueryFn is sufficient or whether a small immutable geometry interface is preferable.
5. Chunk architecture
    * Resolve the distinction between deterministic generation and asynchronous loading.
    * Define what happens when a rules query encounters an unloaded chunk.
    * Ensure unloaded data can never accidentally become traversable.
    * Determine how dirty chunks are persisted before eviction.
6. Viewport architecture
    * Validate ViewportState.
    * Validate world → viewport → pixel transformations.
    * Validate pixel → world input mapping.
    * Determine how viewport follow/dead-zone behavior should interact with authoritative state changes.
7. Rendering boundary
    * Confirm that the renderer receives precomputed visible tiles/entities rather than owning world queries.
    * Determine how virtualization should work without changing gameplay semantics.
8. Exploration → tactical transition
    * Identify exactly what data crosses the boundary.
    * Determine how the active encounter is created from WorldState.
    * Determine how encounter results are committed back.
    * Identify edge cases involving dead entities, moved entities, doors, loot, and persistent mutations.
9. Save/load
    * Determine what must eventually be serialized.
    * Identify anything in the current design that would make deterministic restoration difficult.
10. AI DM compatibility
    * Verify that a future AI DM can describe/generate environments without becoming authoritative over rules.
    * AI should produce world-generation intent/data; the deterministic world/rules systems remain authoritative.
