TASK: Implement Hover / Target Preview for Intelligent Tabletop

Repository:
JerichoOmega/tabletop-platform

Current baseline:
- Commit 5508399 is the current canonical baseline.
- Do NOT regress or redesign the existing gameplay interaction loop.
- Preserve all existing behavior and architecture.
- Current reported baseline: 93 unit tests, 56/56 E2E tests, clean typecheck, clean build.

GOAL

Improve the tabletop interaction UX by adding a clear visual preview when the player hovers/taps a potential target during an active targeting mode.

The player should be able to understand:
1. What they are currently targeting.
2. Whether the target is valid.
3. What action will occur if they select it.
4. Why a target is invalid when appropriate.

This is a UX layer on top of the existing authoritative rules engine. Do NOT move gameplay validation into the UI.

IMPORTANT ARCHITECTURAL RULE

The rules engine remains authoritative.

Use the existing validation functions:
- validateMove()
- validateAttack()
- validateAbility()
- isValidAbilityTarget()
- lineOfSight()
- chebyshev()

Do not duplicate combat/range/target validation logic in React.

The UI may calculate presentation-only information, but whether an action is actually legal must continue to come from the existing engine.

TARGETING MODES

Preserve the existing interaction modes:
- Move
- Attack
- Ability

When no targeting mode is active:
- No target preview should appear.
- Hovering a combatant should not create a targeting state.

ATTACK PREVIEW

When Attack mode is active:

1. Hovering a valid enemy:
   - Clearly highlight the hovered enemy.
   - Show a target indicator/outline.
   - Show that this is a valid attack target.
   - If useful within the existing visual language, show relevant attack information such as:
     - target name
     - distance
     - cover
     - expected action description
   - Use the existing attack validation result rather than inventing validity.

2. Hovering an invalid enemy:
   - Clearly indicate that the target cannot currently be attacked.
   - Preserve the existing targeting mode.
   - Do NOT execute anything.
   - Prefer communicating the actual validation reason where practical:
     - out of range
     - blocked line of sight
     - target dead
     - action already used
     - etc.

3. Hovering a friendly PC while Attack mode is active:
   - Do not treat it as a valid target.
   - Do not execute.
   - Provide a clear invalid-target indication.

4. Moving the pointer away:
   - Remove the temporary target preview.
   - Keep Attack mode active.

ABILITY PREVIEW

When Ability mode is active:

Use the ability's own definition and existing validation.

For hostile abilities such as Fire Bolt:
- Valid enemies receive a hostile-target preview.
- Invalid targets receive an invalid indication.
- Friendly PCs should not become valid targets.

For beneficial abilities such as Healing Touch:
- Valid allies/self receive a beneficial-target preview.
- Enemies must remain invalid.
- Do not allow an enemy click/hover to silently substitute the actor or another target.

The existing targeting metadata should remain the source of truth.

VISUAL LANGUAGE

Use the existing Intelligent Tabletop visual language.

Do NOT introduce an unrelated UI design system.

The preview should be visually obvious but restrained.

Use the existing semantic distinction:
- Attack / hostile targeting → existing red/hostile language
- Beneficial abilities → existing blue/beneficial language
- Invalid target → existing invalid/error language

Do not rely on color alone.

Include another visual cue such as:
- outline
- icon
- cursor/state indicator
- small target marker
- text label

The target preview should feel like a tabletop-game interaction, not a generic web hover effect.

MOBILE / TOUCH

This must work on touch devices as well.

There is no true hover on touch.

For touch:
- Tapping/selecting a combatant while a targeting mode is active should establish the target preview/selection state before execution where appropriate.
- Preserve the existing click-to-execute behavior unless changing it is necessary.
- Do not create a two-tap interaction that makes the current gameplay loop confusing.
- Ensure there is always a clear way to cancel targeting using the existing targeting toggle behavior.

Do not over-engineer touch behavior in this task.

IMPLEMENTATION

First inspect the existing:
- IntelligentTabletop.tsx
- rules.ts
- parser.ts
- existing targeting-related UI/components/styles
- current E2E targeting tests

Reuse existing state where possible.

If necessary, introduce a small typed target-preview state rather than adding stringly-typed state.

Prefer a shape such as:

type TargetPreview =
  | null
  | {
      targetId: string;
      valid: boolean;
      reason?: string;
      distance?: number;
      cover?: boolean;
    };

Do not blindly use this exact shape if the existing architecture has a better equivalent.

The preview state must be transient UI state. It must NOT become part of authoritative GameState.

IMPORTANT:
Do not mutate GameState merely because the user is hovering over a target.

Only execution functions should produce gameplay state changes.
