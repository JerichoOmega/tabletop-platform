# REQUIRED BEHAVIOR

## 1. Automatic distance-based eviction

Implement automatic eviction for `RESIDENT` chunks that are sufficiently far outside the active viewport/prefetch region.

Use the existing canonical hysteresis recommendation:

- Prefetch margin = existing `PREFETCH_MARGIN`
- Eviction threshold = `PREFETCH_MARGIN + 1` chunk distance
- Use Chebyshev chunk distance, consistent with the Phase 3 implementation plan.

Only evict chunks that are:

- `RESIDENT`

Never automatically evict:

- `PINNED`
- `LOADING`

Do not evict the currently required viewport/prefetch chunks.

Eviction should occur after the required prefetch work settles rather than on an arbitrary timer.

Do not introduce timer-based eviction unless the existing architecture makes that absolutely necessary.

---

# 2. Entity data MUST survive eviction

This is critical.

Chunk geometry and world entities are separate systems.

Evicting a chunk must NEVER:

- delete an entity
- recreate an entity with a new identity
- reset HP
- reset position
- reset alive/dead state
- reset any other authoritative entity state
- modify `WorldEntityRegistry`
- modify campaign/world state

Entities remain authoritative in `WorldEntityRegistry`.

Chunk eviction only removes cached/generated geometry.

When the player returns to an evicted region, geometry should be regenerated deterministically while the entity registry supplies the authoritative entity state.

---

# 3. Deterministic regeneration

When a previously evicted chunk becomes resident again:

- It must regenerate using the existing deterministic generation path.
- Do not introduce new randomness.
- Do not mutate the world seed.
- Do not introduce generation state that is not already part of the canonical chunk-generation contract.

Given identical:

- world seed
- chunk coordinates
- generation version/configuration

the regenerated geometry must be equivalent to the geometry before eviction.

Do not solve this by retaining the geometry forever.

The purpose of M2 is specifically to prove that geometry can be discarded and reconstructed safely.

---

# 4. Resident chunk bound

The implementation should prevent resident chunks from growing without bound during normal exploration.

After prefetch/eviction settles:

- viewport-required chunks remain resident
- prefetch-margin chunks remain resident
- pinned chunks remain resident
- distant unpinned resident chunks are evicted

Add a test proving the resident set remains bounded according to the existing viewport/prefetch model, plus pinned chunks where applicable.

Do not over-optimize beyond what the existing architecture requires.

---

# 5. Preserve encounter pinning semantics

Existing encounter pinning is authoritative.

M2 must not break the existing behavior where chunks required by an active encounter are pinned.

Verify that:

- pinned chunks cannot be evicted
- moving the viewport does not evict encounter-required chunks
- encounter snapshots remain valid even if unrelated chunks are evicted
- ending an encounter correctly releases its pins through the existing mechanism

Do not redesign encounter pinning.

# TEST REQUIREMENTS

Add focused tests for the new behavior.

## Unit tests

At minimum, cover:

### Eviction selection

Verify:

- near chunks are retained
- prefetch-margin chunks are retained
- distant chunks are selected for eviction
- `PINNED` chunks are immune
- `LOADING` chunks are immune
- already-unloaded chunks are ignored
- eviction selection is deterministic

### Geometry regeneration

Test:

1. Generate chunk.
2. Capture its immutable geometry representation.
3. Evict chunk.
4. Re-resident the same chunk.
5. Generate/read its geometry again.
6. Assert equivalent geometry.

### Entity survival

Test:

1. Create a world entity in a chunk.
2. Record its world ID, position, HP, and relevant authoritative state.
3. Evict the chunk containing it.
4. Verify the entity remains in `WorldEntityRegistry`.
5. Change/verify authoritative state as appropriate.
6. Re-resident the chunk.
7. Verify the entity retains exactly the same identity and state.

The test must demonstrate that entity persistence is independent of chunk residency.

### Pinned entity/encounter behavior

Verify an entity involved in a pinned encounter remains protected from eviction through the existing pinning mechanism.

Do not create a duplicate pinning architecture.
