Task: Lock Down the Gameplay Interaction Loop

The asset registry work in commit 1c825d3 is complete and verified:

* pnpm typecheck clean
* pnpm test 82/82
* pnpm build clean
* pnpm test:e2e 10/10

Now focus on regression protection for the tabletop’s core interaction loop.

Objective

Add automated coverage that ensures future UI, asset, and engine changes cannot silently break the fundamental gameplay interactions.

Do not redesign the UX or add new gameplay features in this task. Preserve the current behavior exactly.

Cover these interaction paths

1. Active actor
    * Correct actor is automatically selected at the start of their turn.
    * The active actor remains visibly marked as ACTING.
    * Selecting an enemy/target does not remove the active-actor state.
2. Movement
    * Enter Move mode.
    * Valid movement tiles become highlighted.
    * Clicking a valid tile performs movement.
    * Invalid/unavailable tiles cannot perform movement.
    * Movement state clears correctly after the action.
3. Attack
    * Enter Attack mode.
    * Valid hostile targets receive the red targeting indicator.
    * Clicking a valid hostile target performs the attack.
    * Friendly/non-targetable units cannot be selected as attack targets.
    * Targeting state clears correctly afterward.
4. Harmful abilities
    * Fire Bolt uses the same hostile/red targeting language as Attack.
    * Valid hostile targets can be selected.
    * Invalid targets cannot be selected.
    * The ability is consumed correctly.
    * The ability button remains visible but disabled after being used.
5. Beneficial abilities
    * Healing Touch uses the blue beneficial targeting language.
    * Valid friendly targets can be selected.
    * Hostile/non-targetable units cannot be selected.
    * The ability is consumed correctly.
    * The ability button remains visible but disabled after being used.
6. Targeting mode transitions
    * Entering one targeting mode clears the previous targeting mode appropriately.
    * Targeting status text matches the active mode.
    * Green/red/blue visual state is always accompanied by explicit instructional text.
    * Canceling/exiting targeting returns the UI to its normal state.
7. End Turn
    * End Turn remains in the primary action row.
    * Ending the turn advances to the correct actor.
    * The new active actor receives the correct ACTING state.
    * The previous actor’s turn-specific action state does not leak into the new turn.
8. Proposal / Query / Inspect
    * Proposal cards remain visually/action semantically distinct.
    * Proposal retains its approval affordance.
    * Query does not expose an Approve action.
    * Inspect remains neutral.
    * Their visual distinctions remain data/state driven rather than dependent on specific text.

Testing requirements

Use the existing testing architecture rather than creating a parallel test framework.

Add tests at the appropriate unit/integration/E2E levels.

Prefer testing observable behavior and state transitions rather than implementation details.

Where practical, make the tests resilient to UI refactoring while still detecting broken gameplay interactions.

Also verify that the tests work with the existing fallback asset behavior introduced by 1c825d3. The asset registry must remain independent of gameplay correctness.

Important architectural constraint

Do not modify the rules engine merely to make tests easier.

Do not bypass the real interaction path with test-only shortcuts.

The tests should exercise the same action/targeting/state flow that an actual player uses.
