ACCESSIBILITY REQUIREMENTS

### 1. Keyboard navigation

Ensure keyboard users can reach and operate:

- Move
- Attack
- End Turn
- abilities
- actionable combatant tokens
- proposal approval/cancellation
- query dismissal
- inspect controls
- encounter selection
- Assisted-mode controls

Use native semantic buttons wherever possible.

Do not replace buttons with clickable divs.

### 2. Focus visibility

Every interactive control needs a clear `:focus-visible` state.

Focus must remain distinguishable from:

- hover
- active actor
- selected target
- valid target
- invalid target

Do not remove browser focus indicators without providing an equivalent visible replacement.

### 3. Board tokens

Interactive combatants must:

- be keyboard focusable
- have meaningful accessible names
- expose relevant state
- have visible focus
- remain compatible with mouse and touch interaction

Examples of useful accessible descriptions:

"Sable, acting"

"Orc, valid attack target"

"Aldric, invalid Fire Bolt target: wrong target type"

Use the actual application's terminology where appropriate.

Do not make decorative board elements unnecessarily focusable.

### 4. Targeting

Preserve the existing semantic targeting system:

Move:
- green visual language
- explicit instruction text

Attack:
- red hostile targeting
- explicit instruction text

Harmful abilities:
- red hostile targeting
- explicit instruction text

Beneficial abilities:
- blue beneficial targeting
- explicit instruction text

Invalid targets:
- explicit invalid indication/reason where available

Never rely on color alone.

The existing target-preview information introduced by `8e966cf` must remain accessible.

Do not create a noisy screen-reader announcement for every pointer movement.

Prefer meaningful state-change announcements.

### 5. Active actor

Preserve the visible `ACTING` indicator.

Make the acting character understandable to assistive technology.

Do not confuse acting, selected, and targeted states.

### 6. Actions and abilities

Disabled actions must remain visible.

Their disabled state must be semantically exposed.

Where practical, expose the reason an action is unavailable.

For example:

"Fire Bolt, unavailable: action already used this turn"

Do not rely only on visual opacity or tooltips.

### 7. Intent cards

Preserve:

Proposal:
- action-oriented
- Approve
- Cancel

Query:
- informational
- no Approve action

Inspect:
- neutral informational state

Ensure their controls are keyboard accessible and their structure is understandable.

If focus management is added, avoid stealing focus unnecessarily.

If a modal-like interaction genuinely requires focus management, return focus sensibly when dismissed.

### 8. Assisted mode

Ensure:

- text input has an accessible label
- Interpret control is keyboard accessible
- errors are understandable
- resulting proposal/query states are accessible

Do not modify the intent architecture.

Do not add LLM functionality.

### 9. Reduced motion

Add an appropriate:

`@media (prefers-reduced-motion: reduce)`

path for any existing/non-essential UI motion.

Do not build the future animation system in this task.

Do not change gameplay timing.

### 10. Touch

The tablet work from `8529cda` must remain intact.

Do not introduce hover-only functionality.

Touch users must not need hover to understand targeting.

Do not introduce gesture navigation or camera panning.

ARCHITECTURAL RULE

Accessibility is presentation/interaction infrastructure.

Do not put accessibility state into authoritative `GameState`.

Do not modify combat legality for accessibility.

Do not move validation into the UI.

Keep:

GameState
    ↓
Rules / validation
    ↓
UI state
    ↓
Accessible presentation
