Replit Task — Asset Registry Foundation + Documentation Sync

Before making any changes, inspect the current repository state on main and treat the existing engine architecture as authoritative. Do not rewrite or restructure the rules engine, combat system, intent system, or current UX implementation.

Objective

Prepare the tabletop platform for production visual assets by creating a data-driven asset registry that cleanly separates visual assets from game rules/content.

The goal is:

Game Content Definition
        ↓
visual/asset ID
        ↓
Asset Registry
        ↓
Renderer / UI

and not:

Game Content Definition
        ↓
hardcoded image path

Visual assets must never become coupled to combat rules.

⸻

1. Inspect the existing architecture first

Review:

* src/engine/content.ts
* src/engine/rules.ts
* src/intent/parser.ts
* src/ui/primitives.tsx
* src/IntelligentTabletop.tsx
* existing tests
* existing public/ asset structure

Preserve the current four-layer architecture:

* Content
* Rules
* Intent
* UI

Do not move rules into React or introduce visual-asset logic into rules.ts.

⸻

2. Create an asset registry

Create a small, strongly typed asset registry module, preferably under something like:

src/assets/

For example:

src/assets/
├── registry.ts
└── types.ts

Use stable logical IDs rather than filenames as the API.

The registry should be capable of representing at least:

* character/minis
* terrain
* map/floor assets
* props
* future effects/icons where appropriate

Conceptually:

type AssetKind =
  | "character"
  | "terrain"
  | "map"
  | "prop"
  | "effect"
  | "icon";
interface AssetDefinition {
  id: string;
  kind: AssetKind;
  src: string;
  alt?: string;
}

Use whatever exact structure best fits the existing codebase; do not blindly copy this example if a better repository-consistent implementation exists.

⸻

3. Add visual IDs to content definitions

Where appropriate, allow content definitions to reference a visual asset through a stable ID.

For example, a combatant definition should conceptually be able to say:

visualAssetId: "fighter.aldric"

rather than:

image: "/assets/aldric.png"

Likewise, map/terrain definitions should be able to reference visual assets without knowing their filesystem paths.

Do not make visualAssetId required for every existing definition if doing so would create unnecessary churn.

Existing encounters must continue working without requiring production art.

⸻

4. Do NOT hardcode current production art

Do not invent or fabricate asset filenames.

Do not assume that an asset exists simply because an ID has been defined.

The registry must gracefully handle an asset that has not been supplied yet.

For example, a missing visual asset should be able to fall back to the current icon/placeholder rendering.

This is important because production assets are being created separately.

⸻

5. Integrate only at the presentation layer

Update the existing UI so that, when a registered visual asset exists, the presentation layer can resolve it.

The rules engine must remain completely unaware of:

* image paths
* React components
* asset loading
* visual styles
* filenames

The renderer/UI may resolve:

visualAssetId → registered asset → rendered image

but the game rules must only know about the logical content definition.

⸻

6. Preserve the current UX

Do not redesign the tabletop.

Do not change:

* action bar behavior
* targeting colors
* active-turn indication
* proposal/query distinction
* movement
* attacks
* abilities
* turn cycling
* victory/defeat behavior

This task is infrastructure for visual assets, not a UX redesign.

⸻

7. Add tests

Add tests covering at minimum:

1. Valid asset IDs resolve correctly.
2. Unknown asset IDs fail gracefully.
3. Content definitions can reference an asset ID without coupling themselves to a file path.
4. Existing combat behavior is unchanged.
5. Existing encounters still build successfully.
6. Existing UI behavior remains intact.
7. Existing E2E tests continue to pass.

Do not replace deterministic tests with snapshots merely to make the task pass.

⸻

8. Update documentation

docs/PROJECT_STATUS.md is currently behind the implementation.

Bring it up to date with the actual current repository state, including:

* current architecture
* current test infrastructure
* TypeScript status
* Playwright E2E coverage
* victory and defeat fixtures
* current commit/state
* asset registry foundation

Do not claim features are complete unless they actually exist.

In particular, remove obsolete statements claiming that the engine still intentionally relies on @ts-nocheck if that is no longer true.

⸻

9. Verification

Before finishing:

pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e

Fix any regressions introduced by this task.

Do not weaken TypeScript configuration or tests to make them pass.

⸻

10. Commit

Make one focused commit:

feat: add data-driven asset registry foundation

In your final response, report:

* files created
* files modified
* asset registry design
* how content references visual assets
* fallback behavior
* tests added
* typecheck/build/test/E2E results
* commit SHA

Important constraint

Do not proceed into a broader asset pipeline, asset generation system, database, cloud storage system, multiplayer asset synchronization, or major UI refactor.

This task is only establishing the clean architectural seam between game content and visual assets so production assets can be added later without contaminating the rules engine.
