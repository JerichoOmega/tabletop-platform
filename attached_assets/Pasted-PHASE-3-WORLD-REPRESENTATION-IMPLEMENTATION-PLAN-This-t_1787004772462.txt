==================================================
4. REQUIRED ARCHITECTURAL BOUNDARY
==================================================

Before proposing implementation, explicitly preserve this separation:

GAME STATE
    ↓
WORLD STATE
    ↓
VIEWPORT STATE
    ↓
VISIBLE WORLD REGION
    ↓
TABLETOP RENDERING

Rules and gameplay must operate on persistent world state.

Viewport movement must NOT mutate gameplay state merely because the camera moved.

Rendering must be able to unload/reload visual regions without destroying world entities.

An entity must retain its identity and world position even when it leaves the visible viewport.

==================================================
5. IMPORTANT DESIGN CONSTRAINT
==================================================

Do NOT create a giant generalized "world engine."

The roadmap explicitly says:

DO NOT GENERALIZE PREMATURELY.

Only introduce abstractions that Phase 3 actually requires.

If the existing implementation can support the first Phase 3 milestone with a small, explicit abstraction, prefer that over a generalized framework.

For every proposed abstraction explain:

- Why it is required now.
- Which existing code needs it.
- Which Phase 3 requirement it satisfies.
- Why the existing system cannot simply be extended.
- What future systems it intentionally does NOT attempt to solve.

7. VIEWPORT MODEL
==================================================

Determine the minimum viewport model required.

The viewport should describe what portion of the world is currently visible.

Consider:

- world-space position
- visible width/height
- tile dimensions
- camera offset
- viewport bounds
- prefetch margin
- conversion between world and screen/table coordinates

Do not assume the viewport belongs in GameState.

Explicitly identify which values are:

AUTHORITATIVE GAME STATE

versus

PRESENTATIONAL VIEWPORT STATE.

==================================================
9. LONG CORRIDORS AND LARGE AREAS
==================================================

The design must support the core visual behavior:

The tabletop itself stays fixed.

If a player travels down a very long corridor, the world moves through the tabletop viewport.

As the player advances:

- tiles leave the viewport
- new tiles enter
- entities retain persistent world coordinates
- the tabletop does not grow
- the visible world changes

The same architecture must also support:

- small rooms
- large rooms
- wide chambers
- massive battlefields
- long corridors
- outdoor/open areas

Do not solve long corridors with a special-case corridor system.

The viewport/world separation should solve all of these naturally.

==================================================
11. MIGRATION STRATEGY
==================================================

The existing combat system already works.

Therefore Phase 3 must not casually rewrite combat.

Provide a migration strategy that allows the existing game to continue working while world representation is introduced.

Prefer:

existing board
    ↓
world-backed board
    ↓
viewport-backed rendering

rather than:

delete existing board
    ↓
rewrite entire game

Identify compatibility adapters where genuinely necessary.

==================================================
13. PERFORMANCE
==================================================

Identify the expected rendering boundary.

The goal is NOT:

"render the entire world."

The goal is:

"render the visible world plus a small prefetch margin."

Determine:

- expected visible tile count
- expected prefetch region
- when regions should be loaded
- when regions can be discarded
- how to avoid unnecessary React renders
- whether memoization is required
- whether viewport movement should be isolated from GameState updates

Do not optimize prematurely.

Identify measurable performance criteria instead.

15. RISK ANALYSIS
