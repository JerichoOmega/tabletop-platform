OBJECTIVE

Perform a focused accessibility pass on the existing Intelligent Tabletop experience.

The goal is to ensure that the tabletop's existing gameplay, targeting, action controls, intent cards, and responsive layouts remain understandable and operable without relying exclusively on visual color, mouse hover, or precise pointer interaction.

This is an accessibility and interaction-quality task.

Do NOT redesign the tabletop.

Do NOT change gameplay rules.

Do NOT change the combat engine.

Do NOT change targeting semantics.

Do NOT implement World Scale.

Do NOT add new gameplay mechanics.

ACCESSIBILITY PRIORITIES

Prioritize the following areas:

1. Keyboard navigation
2. Focus visibility
3. Board token accessibility
4. Action/ability accessibility
5. Targeting-state communication
6. Active-actor communication
7. Proposal/query/inspect cards
8. Non-color visual communication
9. Touch + keyboard compatibility
10. Reduced-motion support

--------------------------------------------------
1. KEYBOARD NAVIGATION
--------------------------------------------------

Audit the entire primary gameplay loop.

Ensure keyboard users can access:

- Move
- Attack
- End Turn
- Abilities
- Combatant tokens
- Target selection where technically practical
- Proposal Approve
- Proposal Cancel
- Query Dismiss
- Inspect controls
- Encounter selection
- Assisted-mode controls

Use native semantic buttons wherever possible.

Do NOT replace semantic buttons with clickable divs.

Do NOT create a completely custom keyboard-navigation system if normal browser focus behavior is sufficient.

For board tokens:

- They must be keyboard focusable when they represent an actionable/selectable combatant.
- Their accessible name must identify the combatant.
- Their current targeting state must be understandable.
- Focus must be visibly distinguishable.

Example conceptual accessible labels:

"Sable, acting"

"Orc, valid attack target"

"Aldric, invalid Fire Bolt target: wrong target type"

Do not blindly use these exact strings if the existing UI has a better naming convention.

--------------------------------------------------
2. FOCUS VISIBILITY
--------------------------------------------------

Ensure all interactive controls have a clear `:focus-visible` state.

Focus indicators must remain visible against the existing tabletop aesthetic.

Do not remove browser focus outlines without replacing them with an equally or more visible focus treatment.

Pay particular attention to:

- action buttons
- ability buttons
- encounter buttons
- board tokens
- proposal controls
- query controls
- inspect controls
- text inputs
- mode selectors

The focus state must not be confused with:

- active actor
- selected target
- hovered target
- invalid target

These are different states and should remain visually distinguishable.

--------------------------------------------------
3. BOARD TOKEN ACCESSIBILITY
--------------------------------------------------

Audit the existing token implementation introduced/updated by the targeting work.

Each interactive combatant token should have:

- semantic interactive behavior
- accessible name
- keyboard focus
- visible focus state
- current relevant state communicated to assistive technology

Preserve the existing visual states:

- active actor
- selected target
- valid target
- invalid target
- hover preview

Do not remove any existing visual feedback.

When a token is not actionable, it should not incorrectly appear keyboard-actionable.

Do not expose decorative/non-interactive elements as unnecessary interactive controls.

--------------------------------------------------
4. TARGETING STATE
--------------------------------------------------

The current targeting language must remain intact.

Preserve:

Move:
- green movement language
- explicit instruction text

Attack:
- red hostile targeting language
- explicit instruction text

Harmful abilities:
- red hostile targeting language
- explicit instruction text

Beneficial abilities:
- blue beneficial targeting language
- explicit instruction text

Invalid targets:
- explicit reason where available

The player must NOT have to distinguish targeting modes solely through color.

The existing target-preview line such as:

"⊕ Orc · 4 tiles"

or:

"⊘ Aldric: wrong target type"

should remain available visually.

Improve its accessibility where appropriate.

Do not create excessive live-region announcements for every pointer movement.

For example, hovering over ten enemies should not cause ten intrusive screen-reader announcements.

Prefer announcing meaningful targeting-state changes.

--------------------------------------------------
5. ACTIVE ACTOR
--------------------------------------------------

The existing `ACTING` indicator must remain visible.

Ensure the active actor is also understandable to assistive technology.

A user should be able to determine:

- whose turn it is
- which actor is acting
- which token is currently active

Do not confuse:

ACTING

with:

TARGET

or:

SELECTED

These remain separate concepts.

--------------------------------------------------
6. ACTION BUTTONS
--------------------------------------------------

Audit:

- Move
- Attack
- End Turn
- ability buttons

Ensure disabled buttons communicate their disabled state semantically.

Existing behavior must remain:

- disabled actions stay visible
- disabled actions do not disappear
- disabled actions retain their current visual treatment

Where an action is disabled because it has already been used, make that reason available accessibly.

For example:

"Fire Bolt, unavailable: action already used this turn"

Do not rely only on the tooltip.

--------------------------------------------------
7. PROPOSAL / QUERY / INSPECT CARDS
--------------------------------------------------

Preserve the existing semantic distinctions:

Proposal:
- action-oriented
- amber/warm visual treatment
- Approve
- Cancel

Query:
- informational
- blue/cool visual treatment
- no Approve action
- Dismiss where appropriate

Inspect:
- neutral informational treatment

Ensure:

- headings are semantically structured
- buttons have clear accessible names
- card state is understandable
- proposal approval is not confused with informational content
- focus moves logically when a card appears

Do not automatically steal focus unless it materially improves keyboard accessibility.

If focus management is added, ensure that dismissing the card returns focus to a sensible originating control.

--------------------------------------------------
8. FORMS / ASSISTED MODE
--------------------------------------------------

Audit the Assisted-mode text input and interpretation controls.

Ensure:

- textbox has an accessible label
- Interpret action is keyboard accessible
- errors/invalid interpretations are understandable
- proposal/query results are accessible
- focus behavior is sensible after interpretation

Do not change the intent architecture.

Do not add LLM functionality.

--------------------------------------------------
9. COLOR AND CONTRAST
--------------------------------------------------

Review the existing tabletop colors for meaningful UI states.

Do not redesign the palette.

Ensure important state is communicated using more than color.

Examples:

- red + hostile target indicator
- blue + beneficial target indicator
- green + movement instruction
- amber + invalid/attention state
- ACTING badge + text
- ✓ / ✗ target indicators
- explicit targeting instructions

Preserve the existing visual language.

If a specific state currently depends entirely on color, add a minimal secondary cue.

--------------------------------------------------
10. REDUCED MOTION
--------------------------------------------------

Introduce a reduced-motion path for future/current UI transitions where appropriate.

Use the standard:

`@media (prefers-reduced-motion: reduce)`

Do not add a large animation system in this task.

The purpose is to ensure that if animation is introduced later, the architecture has an appropriate accessibility path.

If the current implementation has animations, reduce or disable non-essential motion under reduced-motion preferences.

Do not alter gameplay timing.

--------------------------------------------------
11. TOUCH + KEYBOARD
--------------------------------------------------

The tablet-responsive work from `8529cda` must remain intact.

Do not break:

- touch interaction
- tap targets
- tablet layout
- targeting
- target preview

Keyboard focus and touch interaction must coexist.

Do not introduce hover-only functionality.

Remember:

Touch devices do not have reliable hover.

The current gameplay interaction must remain understandable without hover.

--------------------------------------------------
12. ACCESSIBLE STATE VS GAME STATE
--------------------------------------------------

Accessibility state must not become authoritative gameplay state.

Do NOT add accessibility-only state to `GameState`.

Do NOT modify combat rules to support screen readers.

Do NOT move validation into accessibility components.

The architecture remains:

GameState
    ↓
existing rules / validation
    ↓
UI state
    ↓
accessible presentation

Accessibility is a presentation layer.

--------------------------------------------------
13. TESTING
--------------------------------------------------

Add automated regression coverage where practical.

At minimum test:

### Keyboard

- Tab can reach primary action controls.
- Enter/Space activates appropriate buttons.
- Disabled actions cannot be activated.
- Focus remains visibly represented.

### Board tokens

- Interactive tokens are keyboard focusable.
- Accessible names identify combatants.
- Active actor state is exposed.
- Valid/invalid targeting state is exposed where appropriate.

### Targeting

- Move mode is understandable without color.
- Attack mode is understandable without color.
- Beneficial ability targeting is understandable without color.
- Invalid target reason is accessible where available.

### Active actor

- `ACTING` remains visible.
- Accessible representation identifies the acting character.

### Intent cards

- Proposal Approve/Cancel are keyboard accessible.
- Query Dismiss is keyboard accessible.
- Inspect controls are keyboard accessible.
- Focus behavior remains sensible when cards appear/disappear.

### Responsive regression

Run the existing responsive tests from `8529cda`.

Do not break desktop, tablet landscape, or tablet portrait behavior.

--------------------------------------------------
14. TESTING STRATEGY
--------------------------------------------------

Prefer semantic assertions such as:

- getByRole()
- getByLabel()
- getByText()

Avoid tests that depend on exact pixel positions.

Do not make accessibility tests brittle by requiring implementation-specific DOM structures unless necessary.

Do not weaken existing tests.

Do not remove existing tests.
