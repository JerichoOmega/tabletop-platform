Core architectural rule

The async chunk system must never make the rules engine asynchronous.

The architecture must remain:

ASYNCHRONOUS WORLD INFRASTRUCTURE
ChunkStore
   ↓
async load/generation
   ↓
RESIDENT chunks
   ↓
immutable snapshot barrier
   ↓
─────────────────────────────
SYNCHRONOUS SIMULATION
   ↓
ResidentGeometrySnapshot
   ↓
TileQueryFn
   ↓
GameState
   ↓
rules engine

Never implement:

TileQueryFn → await ChunkStore

Never allow:

rules → await chunk

Never allow GameState.tileQuery to close over the live ChunkStore.

2. Add the LOADING lifecycle

UNLOADED
    ↓
LOADING
    ↓
RESIDENT

while preserving:

RESIDENT
    ↓
PINNED
    ↓
RESIDENT

A chunk must never be simultaneously represented as multiple contradictory residency states.

3. Make loading asynchronous

Introduce an asynchronous loading/generation boundary.

The exact API should follow the repository’s existing conventions, but conceptually it should support:

await chunkStore.ensureResident(cx, cy)

or the equivalent specified by WORLD_SCALE_VIEWPORT.md.

Loading may involve deterministic chunk generation.

The important requirement is:

request
  ↓
LOADING
  ↓
async generation/load
  ↓
RESIDENT

Do not expose a partially constructed ChunkGeometryData as resident.

A chunk becomes RESIDENT only after its complete immutable geometry has been produced successfully.

⸻

4. Deduplicate concurrent loads

This is mandatory.

If two callers request the same unloaded chunk concurrently:

request A ──┐
            ├── same chunk
request B ──┘

they must share the same in-flight operation rather than independently generating/loading the chunk twice.

The store should conceptually maintain:

chunk key
    ↓
in-flight Promise

while the chunk is LOADING.

Verify:

ensureResident(A)
ensureResident(A)

results in one actual generation/load operation and two callers receiving the same completed resident chunk.

⸻

5. Handle loading failures correctly

Define and implement failure behavior.

If asynchronous generation/loading fails:

LOADING
    ↓
failure
    ↓
UNLOADED

unless the specification explicitly requires another recovery state.

Do not leave a permanently stuck LOADING chunk.

Do not mark a failed chunk RESIDENT.

Do not expose partial geometry.

Do not silently convert an infrastructure failure into a valid gameplay tile.

Ensure a subsequent request can retry loading the chunk.

Add tests for:

* successful load
* failed load
* retry after failure
* concurrent callers sharing one load

⸻

6. Preserve deterministic generation

Continue using the existing isolated chunk-generation RNG.

Async scheduling must not affect generated geometry.

These must produce identical geometry:

load A → load B

and:

load B → load A

and:

load A and B concurrently

Generation order must never affect chunk contents.

The gameplay RNG must remain completely untouched.

Add a regression test proving that asynchronous chunk loading does not alter an independent gameplay RNG sequence.

⸻

7. Preserve immutable geometry

Once generation completes:

ChunkGeometryData

must remain immutable.

Async loading must never expose mutable intermediate structures to consumers.

The lifecycle should be:

generate mutable working data
      ↓
finalize
      ↓
immutable ChunkGeometryData
      ↓
RESIDENT

Add explicit regression tests.

⸻

9. Snapshot creation must be residency-safe

Do not allow:

snapshot creation
      ↓
missing required chunk

to happen accidentally because a chunk is still LOADING.

A snapshot request must either:

1. occur only after all requested chunks are known to be RESIDENT, or
2. use an explicit asynchronous preparation operation that waits for all required chunks.

The resulting snapshot itself remains synchronous and immutable.

Do not make snapshotToTileQuery() asynchronous.

⸻

10. Pinning during asynchronous loading

Carefully handle:

UNLOADED
    ↓
request pin
    ↓
LOADING
    ↓
RESIDENT
    ↓
PINNED

If the API allows a caller to request a pinned chunk before loading finishes, ensure there is no race where:

* the chunk becomes resident
* eviction runs
* the chunk is evicted
* the original caller then receives it

A requested encounter-required chunk must become protected as part of the residency transaction.

Define and test the exact ordering.

⸻

11. Eviction safety

Preserve the existing invariant:

PINNED → cannot evict

Also ensure:

LOADING → cannot evict

unless the architecture explicitly defines cancellation.

Do not introduce cancellation unless it is actually required.

Simpler is preferable here:

LOADING
    ↓
complete
    ↓
RESIDENT

followed by normal eviction rules.
