INTELLIGENT TABLETOP — CORE PRESENTATION & CAMERA DIRECTION

This is an architectural/design directive for the current project.

We have now established the intended overall visual experience of Intelligent Tabletop.

DO NOT implement the entire presentation system yet unless the repository is already ready for it.

Instead, make sure the current architecture does not work against these decisions.

==================================================
1. THE GRAND GAMING TABLE IS THE PHYSICAL FOUNDATION
==================================================

The canonical asset:

tabletop.grand-gaming-table-v1

represents the physical gaming table around which the players conceptually sit.

The table is not merely decorative scenery.

It establishes the physical context of the game.

The intended presentation has two major camera states:

ZOOMED OUT:
- The Grand Gaming Table is visible.
- The surrounding room/environment can be visible.
- Players sitting around the table can eventually be represented.
- The dungeon exists on the tabletop.

ZOOMED IN:
- The physical table largely leaves the camera framing.
- The camera focuses on the tabletop battlefield.
- The player sees the dungeon/map and miniatures.

The two views represent different camera distances within the SAME physical environment.

Do not create two disconnected scenes.

==================================================
2. SHARED GROUP TACTICAL PERSPECTIVE
==================================================

The gameplay camera is a shared tabletop perspective.

It is NOT:

- a first-person character camera
- a third-person character camera
- an individual character-follow camera
- a conventional RPG character perspective

The entire group is effectively looking down at the same battlefield.

Players should perceive:

- walls
- floors
- terrain
- props
- miniatures
- enemies
- objectives
- tactical positions

from the shared tabletop perspective.

The tactical camera should therefore remain independent of individual character entities.

==================================================
3. MINIATURES ARE TABLETOP OBJECTS
==================================================

For the current implementation, miniatures are STATIC tabletop objects.

They:

- remain on their circular bases
- have a defined facing/orientation
- occupy a gameplay position/tile
- move as complete miniature pieces
- do not currently need walking animations
- do not currently need attack animations
- do not currently need idle animations

The gameplay object should conceptually be:

Character Entity
    ↓
Position / Tile
    ↓
Miniature Representation
    ↓
Circular Base

Movement should move the miniature/base from one tabletop position to another.

==================================================
4. FUTURE ANIMATION MODEL
==================================================

Do not implement this yet unless necessary.

However, the architecture must allow future animation.

Eventually:

Character Entity
    ↓
Gameplay State
    ↓
Miniature Anchor/Base
    ↓
Animated Visual Representation

The rules engine should NOT know about:

- walking animation
- attack animation
- idle animation
- death animation
- spell animation

Those belong to the rendering/animation layer.

The base remains the gameplay anchor.

==================================================
5. ZOOM IS A PRESENTATION TRANSITION
==================================================

Zooming should eventually move continuously between:

TABLE VIEW
    ↓
TABLETOP VIEW
    ↓
TACTICAL ENCOUNTER VIEW

These are not separate game modes.

They are different camera distances within the same physical tabletop environment.

Do not implement a completely separate "battle scene" that disconnects the dungeon from the Grand Gaming Table.

==================================================
6. CURRENT IMPLEMENTATION PRIORITY
==================================================

DO NOT stop current gameplay development to build the complete camera/table/player presentation system.

For now:

- preserve the existing gameplay architecture
- keep the Grand Gaming Table registered
- keep terrain modular
- keep miniatures represented as static tabletop objects
- ensure camera/rendering architecture does not assume an individual-character perspective
- avoid hard-coding gameplay to a full-screen flat map
- keep rendering concerns separate from the rules engine

The actual camera/presentation layer can be implemented as a dedicated future feature.

==================================================
7. ARCHITECTURAL PRINCIPLE
==================================================

The intended conceptual hierarchy is:

Physical Gaming Table
        ↓
Tabletop Play Surface
        ↓
Modular Dungeon / Battlefield
        ↓
Miniatures + Props + Terrain
        ↓
Gameplay State

The rules engine operates on the gameplay state.

The renderer presents that state as a physical tabletop.

Do not reverse this relationship.

==================================================
8. IMPORTANT VISUAL GOAL
==================================================

The final experience should feel like:

"We are sitting around a magical/highly sophisticated fantasy tabletop playing a real tabletop RPG."

It should NOT feel like:

"We are playing a conventional tactical RPG that happens to use miniature graphics."

The tabletop itself is part of the identity of the product.

==================================================
9. DOCUMENTATION
==================================================

Add these principles to the appropriate project/design documentation.

Document:

- shared tabletop perspective
- Grand Gaming Table as foundational environment
- zoomed-out table view
- zoomed-in tactical view
- static miniature phase
- future miniature animation phase
- miniature base as gameplay anchor
- separation between gameplay state and animation/rendering

Do not create a new implementation system solely for documentation.

==================================================
10. FINAL RULE
==================================================

We are establishing the design direction now.

We are NOT asking for the complete camera/player/animation implementation yet.

Make the architecture compatible with this direction and document it so future implementation does not accidentally turn Intelligent Tabletop into a conventional character-centric tactical RPG.
