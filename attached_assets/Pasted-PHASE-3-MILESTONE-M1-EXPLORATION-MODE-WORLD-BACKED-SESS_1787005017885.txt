==================================================
GOAL
==================================================

Make the existing world/viewport/streaming infrastructure LIVE during an actual tabletop exploration session.

The goal is NOT to build a new world engine.

The goal is:

Persistent World
      ↓
Exploration Session
      ↓
Viewport
      ↓
Visible World
      ↓
Tabletop

A player should be able to explore a world larger than the fixed tabletop viewport.

The tabletop remains fixed.

The world moves through it.

==================================================
2. DO NOT REDESIGN THE STREAMING ENGINE
==================================================

The existing viewport/streaming architecture has already been implemented.

Reuse it.

Do NOT:

- replace WorldCoord
- replace WorldState
- rewrite chunk calculation
- rewrite viewport streaming
- create a second viewport system
- create a second coordinate system
- move viewport state into GameState
- redesign the existing renderer unnecessarily
- rewrite combat to accommodate exploration

If an existing abstraction is insufficient, identify the smallest required change and explain why before making it.

==================================================
3. EXPLORATION MODE
==================================================

Introduce the minimum exploration-session layer required to make the world representation observable and playable.

Exploration should represent:

- the party's persistent world position
- the current viewport
- visible world content
- movement through the world
- exploration state
- transition opportunities into encounters

Do NOT build a full RPG exploration system.

No:

- quests
- inventory overhaul
- faction systems
- procedural world generation
- dialogue system
- crafting
- survival mechanics
- campaign progression

Those belong to later phases.

==================================================
4. WORLD-BACKED SESSION
==================================================

The exploration session must use the existing world representation rather than a fixed encounter map.

The player's location must be represented in world coordinates.

Moving the player should cause the viewport to follow the player or otherwise update according to the existing viewport contract.

The important distinction is:

GAMEPLAY POSITION
=
WORLD COORDINATE

DISPLAY POSITION
=
VIEWPORT/TABLETOP COORDINATE

Never substitute one for the other.

==================================================
5. FIXED TABLETOP
==================================================

The tabletop itself must remain a fixed-size presentation surface.

When the player moves:

- the tabletop does not expand
- the board does not become larger
- the viewport moves through the world
- tiles enter and leave the visible region
- the player's world coordinate persists

This must work for:

- long corridors
- large rooms
- wide areas
- multi-region spaces

Do not create corridor-specific logic.

==================================================
6. MINIMUM EXPLORATION INTERACTION
==================================================

Implement only enough interaction to prove the architecture works.

At minimum:

- player can see their current location
- player can move through world space
- viewport updates
- visible world changes
- world coordinates remain correct
- the same entity remains the same entity while moving
- existing tabletop interaction conventions remain intact

If the existing architecture already provides movement primitives, reuse them.

Do not create a parallel movement system.

==================================================
7. SESSION STATE BOUNDARY
==================================================

Be explicit about state ownership.

AUTHORITATIVE:

- world coordinates
- entity identity
- world entity state
- exploration state required for gameplay

PRESENTATIONAL:

- viewport position
- visible chunks
- camera offsets
- hover state
- animation state
- rendering-only information

Viewport movement must never accidentally mutate authoritative gameplay state.

==================================================
8. EXISTING COMBAT MUST SURVIVE
==================================================

Do not rewrite the existing combat system.

Existing encounters must continue to work exactly as before.

Exploration should eventually transition INTO combat rather than replacing combat.

For this milestone, only establish the minimal contract necessary for a future:

Exploration
    ↓
Encounter Trigger
    ↓
Combat Session

Do not implement the complete transition unless the existing architecture already makes it trivial and it is explicitly part of M1.

M5 handles the complete exploration → encounter → combat transition.

==================================================
9. TESTING
==================================================

Add tests only for M1 behavior.

Unit tests should verify:

- exploration session initialization
- world position initialization
- movement updates world position
- viewport follows/updates correctly
- world position and viewport position remain distinct
- visible-region calculation remains correct

E2E tests should verify at minimum:

1. Exploration session loads.
2. Player is visible.
3. Player can move.
4. World/viewport changes as the player moves.
5. Tabletop dimensions remain fixed.
6. Player identity persists after movement.
7. Existing combat remains functional.
8. Existing tabletop regression tests remain green.

Do NOT weaken or remove existing tests.

==================================================
10. PERFORMANCE
==================================================

Use the existing viewport streaming implementation.

Do not render the entire world.

The visible region plus the existing prefetch strategy should remain the rendering boundary.

Avoid introducing:

- unnecessary global state
- per-frame React state updates
- full-world rerenders
- duplicated coordinate calculations

Measure before optimizing.
