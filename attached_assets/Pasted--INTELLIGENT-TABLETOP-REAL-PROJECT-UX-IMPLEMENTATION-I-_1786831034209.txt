==================================================
PHASE 4 — INVESTIGATE TARGET CLICK PRIORITY
==================================================

The UX Blueprint specifically identifies a real interaction issue:

While an action such as Move, Attack, or Ability is pending, clicks on board tokens must first be interpreted through the pending action's targeting rules.

Only if the pending action does not apply should the click fall back to ordinary character selection.

This is especially important for ability targeting.

The desired interaction is:

NORMAL:
click character → select character

ATTACK MODE:
click enemy → target enemy

ABILITY MODE:
click valid ability target → target that character

MOVE MODE:
click destination → attempt movement

Do not let normal character-selection behavior swallow a pending action's target click.

This should be implemented in a way that remains compatible with future actions and abilities.

Do not hardcode a special case such as:

if ability === "Healing Touch"

Instead, route the interaction based on the current pending action/targeting rules.

==================================================
IMPLEMENTATION ORDER
==================================================

Implement the blueprint in this order:

### 1. TARGETING CLICK PRIORITY

Fix pending-action target routing first.

This is the highest priority because it directly affects whether players can actually operate the tabletop.

Verify:

- Move
- Attack
- Healing Touch
- Fire Bolt
- invalid target feedback

before moving on.

--------------------------------------------------

### 2. ACTION BAR SCALABILITY

Implement the blueprint's two-tier action bar.

Tier 1:

- Move
- Attack
- End Turn

These remain consistently available when appropriate.

Tier 2:

- data-driven abilities

Abilities should continue to come from the character's ability data.

Do not hardcode ability buttons.

The ability area should support approximately 8–10 abilities without pushing End Turn off-screen.

Use the blueprint's proposed behavior:

- wrap up to two rows
- then horizontally scroll when necessary

Do not let the action bar grow indefinitely.

Disabled actions should remain visible and explain why they are disabled.

Ability tooltips should derive information from the ability's data rather than hardcoded UI text.

--------------------------------------------------

### 3. TARGETING VISUAL LANGUAGE

Implement distinct targeting states.

Movement:
GREEN / movement language

Attack:
RED / hostile targeting language

Beneficial ability:
COOL BLUE / friendly targeting language

Harmful ability:
same hostile targeting language as attacks

Do not rely on color alone.

Pair important states with:

- shape
- icon
- text
- other visual signals

The board should clearly communicate:

"Where can I move?"

"What can I attack?"

"Who can I help?"

without forcing the player to read a paragraph.

--------------------------------------------------

### 4. ACTIVE TURN VS SELECTED CHARACTER

Separate these concepts visually.

Selected character:
the character whose panel is currently open.

Active character:
the character whose turn it currently is.

They may normally be the same, but they must remain visually distinguishable.

If the player selects another character/enemy to inspect it, the active-turn indicator must remain visible on the actual current actor.

The player should never lose track of whose turn it is.

--------------------------------------------------

### 5. QUERY VS PROPOSAL CARDS

Keep the existing strong itemized validation-card pattern.

But visually distinguish:

PROPOSAL

from:

QUERY / INSPECT

A proposal means:

"An action is pending your approval."

A query means:

"Here is information. Nothing will happen."

Proposal:
- Approve
- Cancel

Query:
- Dismiss
- no Approve button

Keep real validation reasons.

Never invent validation text in the UI.

--------------------------------------------------

### 6. RESPONSIVE TABLET DESIGN

After the above smaller changes are stable, implement the tablet layout from the blueprint.

Keep the board centered.

Party/action controls should become a persistent bottom bar.

Initiative should become a slim strip above the board.

Session log can become collapsible.

Command bar should remain reachable.

Do NOT simply stack all desktop columns vertically.

The board must remain the centerpiece.

--------------------------------------------------

### 7. RESPONSIVE PHONE DESIGN

Then implement the phone layout.

The board should occupy most of the screen.

Use:

- compact party information
- expandable action sheet
- compact turn indicator
- expandable session log
- command-bar expansion

Do not push the board below a pile of vertically stacked panels.

The tabletop should still feel like a tabletop on a phone.

--------------------------------------------------

### 8. HOVER / LONG-PRESS TARGET PREVIEW

Add this after the core fixes.

For valid targets, allow the player to see a small contextual preview such as:

Fire Bolt → Goblin 1

or:

Healing Touch → Aldric

This should be derived from the same validation/action data already used for execution.

It must not create a second rules system.

--------------------------------------------------

### 9. ACCESSIBILITY PASS

After the visual language is stable:

- verify contrast
- do not rely on color alone
- maintain explicit text/state indicators
- ensure comfortable touch targets
- preserve readable secondary stats
- ensure targeting states have non-color distinctions

The blueprint specifically calls out approximately 44px-equivalent touch targets as a design constraint.

==================================================
ANIMATION / FEEDBACK
==================================================

Implement animation carefully.

The blueprint's principle is:

EVERY ANIMATION SHOULD COMMUNICATE A STATE CHANGE.

Do not add decorative animation everywhere.

Where practical:

Selection:
immediate visual change.

Turn start:
brief active-character pulse.

Movement:
animate the token along the actual path.

Attack:
brief directional cue synchronized with resolution.

Casting:
similar directional cue, differentiated through ability targeting language.

Healing:
brief restorative feedback and visible HP-bar refill.

Damage:
brief HP-bar drain.

Death:
brief fade/removal.

Invalid action:
feedback banner rather than excessive board shake.

Proposal approval:
proposal dismissal should feel connected to the resulting action.

Victory:
stronger celebratory banner.

Animations should be short, non-blocking, and never prevent the player from taking the next action.
