M7 / Phase 3 M5 — SEAMLESS EXPLORATION ↔ COMBAT LOOP

Repository:
JerichoOmega/tabletop-platform

IMPORTANT CONTEXT

The repository currently contains two mature, independently validated halves of the RPG:

1. A world/exploration system:
   - WorldState
   - exploration session
   - party movement
   - viewport following
   - chunk streaming/eviction
   - WorldBounds
   - entity survival
   - hostile proximity detection

2. A combat system:
   - deterministic combat rules
   - initiative/turn order
   - attacks
   - abilities
   - enemy AI
   - deterministic RNG
   - combat termination
   - authoritative victory/defeat handling
   - WorldState.endEncounter()

The problem is that these two systems do not currently form one continuous player-facing loop.

Currently:

EXPLORATION
    ↓
hostile proximity detected
    ↓
placeholder / no transition

Separately:

Encounter Picker
    ↓
Combat
    ↓
Victory
    ↓
"New Encounter"

This is not the intended final gameplay model.

The next milestone is specifically to CONNECT these systems.

==================================================
1. CORE DESIGN DECISION
==================================================

LOCK THIS AS THE PLAYER-FACING RPG LOOP:

EXPLORE
   ↓
DISCOVER / APPROACH
   ↓
COMBAT TRIGGER
   ↓
TACTICAL COMBAT
   ↓
VICTORY / DEFEAT
   ↓
RETURN TO EXPLORATION
   ↓
CONTINUE EXPLORING

Exploration is the persistent primary game state.

Combat is a temporary gameplay state entered from exploration.

Combat is NOT a sequence of unrelated encounter screens.

The player should eventually feel like they are traversing one continuous tabletop adventure.

==================================================
2. PLAYER EXPERIENCE
==================================================

The intended conceptual experience is a hybrid of:

- old-school Final Fantasy-style overworld exploration/encounter flow
- simplified Baldur's Gate 3-style tactical combat

Do NOT copy either game.

Use the following principles:

FINAL FANTASY-LIKE PRINCIPLE:
The party traverses an overworld/adventure area and encounters threats as part of exploration.

SIMPLIFIED BG3-LIKE PRINCIPLE:
Once combat begins, positioning, terrain, movement, abilities, initiative, and tactical decisions matter.

The result should feel like:

"An adventuring party moving around a physical tabletop world that occasionally becomes a tactical battlefield."

==================================================
3. EXPLORATION IS THE PRIMARY STATE
==================================================

The player should spend the majority of the session in an exploration state.

During exploration:

- the party exists in WorldState
- party members have actual world positions
- the viewport follows the party
- movement is constrained by WorldBounds
- terrain remains authoritative
- world entities remain persistent
- enemies/points of interest exist in the world
- the player can choose where to go

Do NOT replace exploration with an encounter menu.

Do NOT require the player to manually select the next encounter.

==================================================
4. REMOVE THE PLAYER-FACING "NEXT ENCOUNTER" FLOW
==================================================

The current post-combat:

"New Encounter"

button is development scaffolding.

It must no longer be the normal continuation of gameplay.

After a successful combat, the player should automatically return to exploration.

The intended flow is:

COMBAT VICTORY
    ↓
authoritative combat termination
    ↓
WorldState.endEncounter()
    ↓
commit surviving combatant state
    ↓
remove defeated entities
    ↓
restore exploration state
    ↓
return player control
    ↓
continue exploring

There should be NO requirement for:

"Click New Encounter"

to continue.

If the existing encounter picker is useful for development/testing, preserve it only as clearly isolated developer/test tooling.

Do not remove useful test infrastructure unnecessarily.

==================================================
5. WORLD-BACKED ENCOUNTERS
==================================================

This milestone must begin transitioning encounters from isolated MapDef-driven gameplay toward encounters originating from the actual exploration world.

When an exploration encounter is triggered:

- determine the relevant world location
- determine the involved world entities
- construct the combat encounter from that world state
- establish combatant positions from world coordinates
- enter the existing combat system

Do not create a second combat engine.

Do not duplicate combat rules.

Do not bypass the existing authoritative WorldState lifecycle.

Use the existing combat engine.

==================================================
6. ENCOUNTER TRIGGER
==================================================

The existing hostile proximity detection is the starting point.

Review the existing implementation and determine the cleanest deterministic trigger.

For this milestone, use a simple deterministic rule.

Example:

Party enters the configured trigger radius of a hostile world entity
        ↓
encounter begins

Do NOT build:

- procedural encounter generation
- random encounter tables
- stealth systems
- perception systems
- AI director
- dynamic difficulty
- narrative triggers

Those are future systems.

We only need a deterministic world → combat transition.

==================================================
7. ENCOUNTER TRANSITION
==================================================

When combat begins:

1. Capture the party's current world position.
2. Identify the triggering hostile entity/entities.
3. Create the combat encounter from those world entities.
4. Establish combatant positions.
5. Transition the presentation into tactical combat.
6. Give control to the existing combat system.

The transition should not teleport the player to an unrelated encounter.

The combat should be spatially related to where the party was exploring.

For the initial implementation, a deterministic local encounter placement strategy is acceptable.

Document the strategy.

Do not build a sophisticated encounter-map generator yet.

==================================================
8. COMBAT PRESENTATION

The intended future presentation is:

EXPLORATION VIEW
    ↓
encounter occurs
    ↓
camera/presentation transitions
    ↓
TACTICAL VIEW
    ↓
combat
    ↓
combat resolves
    ↓
camera/presentation returns
    ↓
EXPLORATION VIEW

Do NOT build a major camera overhaul in this milestone.

Use the existing presentation infrastructure wherever possible.

If a clean transition cannot yet be implemented, establish the state boundary and return path without inventing an elaborate camera system.

The important thing is the gameplay state transition.

==================================================
9. MINIATURE / POSITION MODEL
==================================================

The miniature represents the gameplay entity's physical tabletop position.

During exploration:

Character
    ↓
World Position
    ↓
Miniature

During combat:

Character
    ↓
Combat Position
    ↓
Miniature

After combat:

Combat Position
    ↓
World Position
    ↓
Exploration Miniature

The party should NOT be reset to its original spawn position after combat.

If combat occurred near world coordinate:

(12, 18)

then after combat the party should resume exploration at the appropriate resulting world coordinates.

This is essential.

==================================================
10. COMBAT VICTORY
==================================================

Victory must automatically transition back to exploration.

Use the existing authoritative combat termination lifecycle.

The existing:

WorldState.endEncounter()

is currently implemented and tested but has no production caller.

This milestone should wire it into the actual gameplay flow.

Requirements:

- surviving combatants have their resulting state committed
- defeated combatants are removed/marked appropriately
- entity positions are committed
- combat encounter state is terminated
- encounter pins/temporary state are released appropriately
- exploration resumes
- player control returns
- no duplicate termination
- no partial world mutation

Preserve the existing atomic behavior of endEncounter().

Do not rewrite it unless the integration reveals a genuine contract problem.

==================================================
11. COMBAT DEFEAT
==================================================

Define the smallest deterministic defeat behavior needed for this milestone.

Do NOT invent:

- campaign death systems
- resurrection systems
- save/load
- permadeath
- checkpoints
- mission failure graphs

The defeat behavior may initially be a clearly defined terminal/return state.

Document the decision.

Do not allow defeat to leave the application in an inconsistent combat/exploration state.

==================================================
12. EXPLORATION RESUMPTION
==================================================

After combat:

- the exploration world remains loaded
- WorldState remains authoritative
- party position is preserved
- surviving entities remain valid
- defeated entities are no longer treated as active enemies
- viewport follows the party again
- exploration controls become active
- combat controls disappear
- the player can immediately continue moving

There should be no "New Encounter" click required.

This is one of the primary acceptance criteria.

The area should eventually support:

- obstacles
- hostile entities

The designer should determine what exists.

The player determines how they traverse it.

Do not force the player through:

Encounter 1

Instead:

Explore
→ discover something
→ encounter it
→ resolve it
→ continue exploring

==================================================
22. ACCEPTANCE CRITERIA
==================================================

M7 is complete only when:

### Exploration

- player can move around the bounded exploration world
- viewport follows
- party has authoritative world position

### Encounter

- approaching a hostile entity can deterministically start combat
- encounter originates from the exploration world
- combatants have appropriate positions
- no encounter picker is required

### Combat

- existing combat engine is used
- existing turn/ability/AI systems remain functional
- victory and defeat terminate correctly

### Return

- victory automatically returns to exploration
- no "New Encounter" click is required
- party remains at the appropriate world location
- surviving entities persist
- defeated entities no longer participate
- player controls return to exploration
- viewport resumes exploration behavior

### Integrity

- WorldState remains authoritative
- endEncounter remains atomic/idempotent
- WorldBounds remain enforced
- no out-of-world entities are created
- no duplicate combat lifecycle is introduced

### Quality

- existing tests remain green
- new unit tests pass
- new E2E transition test passes
- TypeScript passes
- production build passes

FINAL DESIGN PRINCIPLE
==================================================

The RPG is NOT:

Encounter
→ Fight
→ Next Encounter
→ Fight
→ Next Encounter

The RPG IS:

EXPLORE
→ DISCOVER
→ ENCOUNTER
→ FIGHT
→ RESOLVE
→ RETURN
→ EXPLORE

The world is the persistent stage.

Combat temporarily takes over that stage.

When combat ends, the stage comes back.

The player should feel like they are physically moving miniatures around one continuous tabletop adventure—not selecting a series of disconnected combat arenas.

Keep this milestone narrow, deterministic, testable, and focused on connecting the two systems that already exist.
